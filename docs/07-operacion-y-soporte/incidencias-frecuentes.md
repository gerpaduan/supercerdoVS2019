## 2026-08-04 - Base de datos local `CarniSys` quedo en estado SUSPECT/RECOVERY_PENDING durante una sesion pesada

- **Sintoma**: `sqlcmd`/la app dejaron de poder conectar (`Login failed for user 'sa'... Failed to open the explicitly specified database 'carnisys'`). `sys.databases` mostraba `CarniSys` en `RECOVERY_PENDING`, y el log de errores de SQL Server mostraba la base reiniciando/recuperandose en loop durante horas.
- **Causa probable**: presion de memoria combinada — en paralelo corrian, en dos sesiones distintas sobre el mismo `.\sqlexpress`, (a) una migracion grande de datos (mover/borrar ~102K filas de `dbo.Corte`, ver `docs/DECISIONS.md` 2026-08-05) y (b) una consulta propia de diagnostico (una CTE recursiva sin filtrar, aislada para medir su costo) que quedo 340+ segundos esperando `RESOURCE_SEMAPHORE` antes de matarla a mano. La notebook estuvo con 116-325MB de RAM libre de ~7GB durante ese tramo (Visual Studio Code x2, Chrome, Windows Defender, y las dos sesiones de Claude Code simultaneas). SQL Server probablemente se quedo sin memoria en medio de una escritura grande y corto de forma sucia.
- **Verificacion**: `SELECT state_desc FROM sys.databases WHERE name='CarniSys'` -> `RECOVERY_PENDING`. `EXEC sys.xp_readerrorlog 0,1,N'CarniSys'` mostro multiples ciclos de "Starting up database... Parallel redo..." a lo largo del dia, y logins fallidos repetidos despues de un "Recovery completed" a las 19:00:12 (incluido un intento del usuario mismo, confirmando que tambien perdio acceso desde su sesion).
- **Resolucion**: cerrar la sesion/proceso que mas RAM liberaba (la otra sesion de Claude Code) subio la RAM libre de ~200MB a ~880MB. No hizo falta reiniciar el servicio de SQL Server (tampoco habia permisos de administrador de Windows para hacerlo — `Restart-Service` fallo con "No se puede abrir el servicio", `whoami`/`IsInRole(Administrator)` confirmaron que la sesion no es admin): la base se recupero sola una vez liberada la memoria. Verificado con `DBCC CHECKDB('CarniSys') WITH NO_INFOMSGS, ALL_ERRORMSGS` sin errores, y conteos de filas clave sin cambios respecto a antes del incidente.
- **Leccion**: si `sqlcmd` empieza a tirar timeouts o `Msg 802: insufficient memory available in the buffer pool` en esta maquina, chequear RAM libre (`Get-CimInstance Win32_OperatingSystem`) antes de asumir un bug de datos o de codigo — mismo patron ya documentado el 2026-07-31 mas abajo, pero esta vez escalo hasta tumbar la base entera por la combinacion de dos sesiones pesadas en simultaneo. Si vuelve a pasar y cerrar procesos no alcanza, el siguiente paso (no probado esta vez) es reiniciar el servicio `MSSQL$SQLEXPRESS` desde una sesion con permisos de administrador.

## 2026-07-29 - "Error de instancia" al iniciar sesion en la web

- **Sintoma**: `System.InvalidOperationException: Error de instancia.` en `Utilidades\Conexion.cs` linea 72 (`cn.Open()`) al hacer login.
- **Causa**: en `Web\Config\connectionStrings.config` el `Data Source` estaba escrito `.\\sqlexpress` (doble backslash). El parser de connection strings de .NET no interpreta el backslash como escape, por lo que busca una instancia literal inexistente.
- **Verificacion**: abrir una `SqlConnection` con esa cadena falla; con `.\sqlexpress` devuelve `ServerVersion` y `Database`.
- **Resolucion**: dejar un solo backslash: `Data Source=.\sqlexpress`. El archivo es local y esta fuera de git (ver `connectionStrings.config.example`).

## 2026-07-29 - No se puede finalizar ninguna venta del POS (400 en /Ventas/FinalizarVenta)

- **Sintoma**: al elegir la forma de pago en el POS, SweetAlert muestra "no se pudo finalizar la venta". En produccion, `App_Data\perf-web.log` muestra `status=400 | total=0-9 ms | db=0 ms/0 calls` en el 100% de los intentos desde el 2026-07-28 21:23 en adelante (osea, ni siquiera llega al controller).
- **Causa**: `Web/Filters/ValidateAppAntiForgeryTokenAttribute.cs` es un filtro global (`FilterConfig.RegisterGlobalFilters`) que exige el antiforgery token en `Request.Form` o en el header `RequestVerificationToken`. El `$.ajax()` de `finalizarVenta()` en `forma-pago.js` manda `contentType: 'application/json'` con el body crudo (`JSON.stringify(payload)`), asi que `Request.Form` queda vacio. El auto-inyector global de headers (`modal-request-loading.js`, hook de `ajaxSend`) deberia agregar el header solo, pero en la practica no llega a tiempo/no corre en el flujo del POS y la request siempre se rechaza antes de llegar al controller.
- **Verificacion**: reproducido con un POST manual incluyendo el header `RequestVerificationToken` (tomado del mismo `input#globalAntiForgeryToken` de la pagina) -> pasa el filtro y llega a la logica de negocio. Sin el header -> `400` inmediato, siempre.
- **Resolucion**: en `Web/Scripts/app/forma-pago.js`, el `$.ajax()` que llama a `FinalizarVenta`/`ModificarVenta` ahora lee el token directo del DOM (`#globalAntiForgeryToken input[name="__RequestVerificationToken"]`) y lo manda explicito en `headers: { RequestVerificationToken: ... }`, sin depender del auto-inyector global.
- **CAUSA RAIZ REAL (encontrada tras probar contra produccion con Chrome real vía CDP)**: `Web/Scripts/app/modal-request-loading.js` daba `404` en produccion (`window.ModalRequestLoading` quedaba `undefined` a pesar de que jQuery si cargaba). El archivo existe en el repo y funciona en local porque IIS Express sirve cualquier archivo del disco sin importar el `.csproj`, pero el *publish* de produccion solo empaqueta lo que `Web.csproj` lista explicitamente como `<Content Include>`. Se encontraron **6 archivos JS huerfanos** (en disco, referenciados por vistas reales, pero ausentes del `.csproj` y por lo tanto ausentes de todo deploy): `modal-request-loading.js`, `modal-postmovimiento.js`, `movimientos.js`, `pago-cheques.js`, `pago-ux.js`, `swal-single-confirm.js`. Se confirmo con Views (130/130 ok) y Content/css (7/7 ok) que el resto del proyecto no tiene el mismo problema.
- **Resolucion real**: se agregaron los 6 `<Content Include="Scripts\app\...">` faltantes a `Web.csproj`. El fix puntual en `forma-pago.js` (mandar el header a mano) se mantiene como refuerzo pero ya no es la causa: una vez que `modal-request-loading.js` carga en produccion, el auto-inyector global vuelve a funcionar solo.
- **Leccion**: cualquier archivo nuevo bajo `Web/` creado por una sesion de IA o herramienta externa a Visual Studio (que no pasa por "Add Existing Item") puede quedar fuera del `.csproj` sin que nada avise — funciona perfecto en `local` (IIS Express) y desaparece silenciosamente en cada deploy a produccion. Ante un bug que "solo pasa en produccion", verificar primero si el archivo estatico relevante devuelve 404 ahi (`curl -sk https://carnisys.com/<ruta> -o /dev/null -w "%{http_code}"`) antes de asumir una causa de codigo/logica.

## 2026-07-30 - Lectura de codigos de barra por camara dejo de andar (todas las vistas)

- **Sintoma**: el boton de escanear codigo de barra (icono de barcode) no abrÃ­a la camara ni mostraba error visible, en `Ventas/POS`, `PuntosExpendio/POS`, `Productos/Index` (3 escaners: precio, catalogo global, codigo global) y `Productos/AddOrEdit`. Reportado "hace varios dias".
- **Causa**: `Web/Helpers/SecurityRuntime.cs` manda el header `Permissions-Policy` con `camera=()` desde el commit `8c749537` (2026-07-16, "Refuerza seguridad web y manejo de secretos"). Una politica vacia bloquea `getUserMedia({video})` para **cualquier origen, incluido el propio sitio**, antes de que el navegador muestre el dialogo de permiso — por eso no habia error visible.
- **Causa adicional (side-quest del mismo pedido)**: el motor de deteccion (`Web/Scripts/app/scanner.js`) usaba solo la API nativa `BarcodeDetector` (Shape Detection API), que **no existe en Firefox ni Safari/iOS** — ahi el boton mostraba "Este navegador no soporta BarcodeDetector" incluso con la politica bien configurada.
- **Resolucion**:
  1. `camera=()` -> `camera=(self)` en `SecurityRuntime.cs` (mismo patron que `geolocation=(self)`).
  2. Se vendorizo `@zxing/library@0.23.0` (UMD, `Content/vendor/zxing/zxing.min.js`, agregado a `Web.csproj`) como motor de respaldo para navegadores sin `BarcodeDetector`. `scanner.js` ahora detecta que motor usar en tiempo de ejecucion: Chromium sigue usando `BarcodeDetector` nativo sin cambios; Firefox/Safari/iOS usan `ZXing.BrowserMultiFormatReader.decodeFromStream()` sobre la misma camara, restringido a los mismos formatos (`EAN_13`, `EAN_8`, `CODE_128`, `UPC_A`). La API publica de la clase `BarcodeScanner` no cambio, asi que ninguna vista necesito modificarse mas alla de cargar el script nuevo.
  3. El script de ZXing se agrego en los dos layouts que lo usan (`_LayoutBase.cshtml`, `_LayoutPOS.cshtml`), antes de `scanner.js` — cubre las 4 vistas (5 escaners) sin tocar cada una.
- **Verificacion**: se probo con Chrome real (headless via CDP), sin poder usar camara fisica real: (a) round-trip de ZXing con una imagen EAN-13 real (Wikimedia, valor conocido `5901234123457`) decodificado correctamente con el bundle vendorizado; (b) integracion real de `scanner.js` con `BarcodeDetector` borrado a proposito (simula Firefox/Safari) y una camara falsa (`canvas.captureStream()`): el motor ZXing se activa, procesa frames continuamente (callback disparado cientos de veces), y `cerrar()` libera la camara sin excepciones. No se pudo probar con un lector fisico real ni en Firefox/Safari reales — pendiente de confirmacion del usuario en dispositivo real.
- **Nota**: `decodeFromStream` de esta version de ZXing no devuelve un objeto de control usable (resuelve `undefined`); el corte del escaneo se hace deteniendo el `MediaStream` directamente en `cerrar()`, igual que el motor nativo.

## 2026-07-30 - JS de POS servido desde cache del navegador tras editar el archivo

- **Sintoma**: al probar un fix en `calculadora-billetes.js` en un navegador ya usado antes en la sesion, el comportamiento viejo seguia apareciendo pese a que el archivo en disco y lo que devolvia el servidor (verificado con `curl`) ya tenian el fix.
- **Causa**: los scripts de POS se referencian con cache-busting manual por query string (`calculadora-billetes.js?v=3237`, `pos-cart.js?v=26`, `factura-electronica.js?v=11`). Si se edita el archivo sin subir el numero de version, el navegador sigue sirviendo la copia cacheada de esa URL exacta.
- **Resolucion**: al tocar cualquiera de estos archivos, **subir el numero de `?v=` en TODAS las vistas/layouts que lo referencian** (buscar `grep -rn "nombre-archivo.js?v="` en `Web/Views`), no alcanza con guardar el `.cs`/`.js`.
- **Leccion**: esto no es solo un problema de testing — cualquier usuario real que haya usado la funcion antes del deploy va a seguir corriendo el JS viejo hasta que la version cambie. Regla para el futuro: **todo cambio a un archivo con `?v=` en su tag `<script>` debe incluir el bump de esa version en el mismo commit**, sin excepcion.

## 2026-07-31 - Header del modal "Mis actividades" con altura descomunal en responsive (~890px)

- **Sintoma**: en el POS, abriendo "Mis actividades" (F6) en mobile, el encabezado de filtros ocupaba muchisima altura (controles separados, la tabla quedaba fuera de pantalla).
- **Causa**: `Content/css/custom.css` tiene `.egresos-pos-toolbar { flex-direction: column; }` dentro de `@media (max-width: 767.98px)`, pensado para el toolbar simple de la pantalla "Egresos de Caja" sola. En `Web/Views/Cajas/_MisEgresosCaja.cshtml`, `.egresos-pos-toolbar-main` y `.egresos-pos-toolbar-actions` tienen `flex: 1 1 180px` / `flex: 999 1 680px` — esos numeros estaban pensados como **ancho** (flex-basis en modo fila). Al heredar `flex-direction: column` de la regla generica, el mismo `flex-basis` pasa a interpretarse como **alto**, y `actions` encima tiene `flex-grow: 999` (dominante) → el toolbar terminaba con ~890px de alto medido en Chrome real (390x844), solo para el header.
- **Verificacion**: medido con Chrome real (CDP) el `getBoundingClientRect()` de cada elemento antes y despues del fix: `main` pasaba de 180px a 25px de alto, el toolbar completo de ~890px a 165px.
- **Resolucion**: `flex-direction: row` explicito para `.mis-actividades-modal .egresos-pos-toolbar` dentro del mismo media query, scopeado para no afectar el toolbar simple de "Egresos de Caja" sola (que sigue usando `column` sin problema porque ahi no hay flex-basis en pixeles grandes de por medio).
- **Leccion**: un `flex-basis` en px asume una direccion de flex fija. Si una regla generica en otro archivo puede cambiar `flex-direction` a un breakpoint dado (via CSS de mas alto nivel, no visible en el archivo que se esta editando), ese basis se reinterpreta silenciosamente como el otro eje. Antes de asumir "la altura viene de mi cambio", medir el `flex-direction` computado real del contenedor, no solo leer el CSS del archivo que se toco.
- **Regresion propia detectada por el usuario (mismo cambio)**: al reordenar los botones de filtro ("Todos"/"Egresos de caja"/"Pagos electronicos"/"Cta Cte") en una fila con scroll horizontal (`flex: 0 0 auto`), cada boton igual quedaba ocupando el 100% del ancho del contenedor — solo se veia uno a la vez al scrollear, pareciendo que los demas habian desaparecido. Causa: `custom.css` tiene `.egresos-pos-toolbar .btn { width: 100%; }` en el mismo breakpoint; `flex-basis: auto` (de `flex: 0 0 auto`) **usa el `width` existente como base** en vez de ignorarlo, asi que el `width:100%` heredado seguia ganando. Fix: agregar `width: auto` explicito junto al `flex`. Verificado con Chrome real: los 4 botones vuelven a medir segun su contenido (54px/109px/127px/62px) y entran los 4 sin necesidad de scroll en 390px de ancho. **Leccion**: `flex-basis: auto` no es "ancho automatico puro", delega en la propiedad `width` si esta esta declarada en otro lado — al tocar `flex` de un elemento hay que revisar tambien si algo mas en la cascada le fija `width` explicito.

## 2026-08-01 - /Stock/ExistenciaPorSucursales no carga / demora excesiva

- **Sintoma**: el usuario reporto que `/Stock/ExistenciaPorSucursales` "no carga" y tiene una demora excesiva al presionar Buscar.
- **Causa**: el stored procedure `dbo.a_ExistenciaStockPorSucursales` recibe `@idEmpresa` pero solo lo usa para filtrar `#Sucursales` — nunca lo usa para filtrar `dbo.Corte` (ni en el mapa de jerarquia de cortes `#MapaCorte`, ni en el armado de productos a mostrar `#AllCortes`). `dbo.Corte` tiene una politica RLS (`RLS_Empresa`, funcion `fn_rls_empresa_o_global_v2`) que **a proposito** deja ver tanto los cortes de la empresa como los del catalogo global (`idEmpresa = 0`) — eso esta bien, es el diseño multi-tenant. El problema es que el SP nunca acota mas alla de lo que la RLS deja pasar: en esta base, de 101.999 cortes visibles bajo RLS, solo 56 son realmente de la empresa (idEmpresa=1) y los otros 101.943 son del catalogo global, nunca adoptados. El `CROSS JOIN` de `#AllCortes` armaba la matriz de stock tambien para esos ~101.900 productos ajenos.
- **Verificacion**: ejecutando el SP a mano contra la base local con `SET STATISTICS TIME ON`: **6.8 segundos**, **203.977 filas** devueltas (101.941 cortes con `independiente=1 AND enCierreStock=1` visibles bajo RLS × ~2 sucursales). Ese resultado despues se procesa en memoria en `Negocio/Corte.cs` (`ObtenerMatrizExistenciaPorSucursales`, agrupando por producto y sucursal) y se renderiza como tabla HTML — con 200K+ filas de entrada, el navegador se cuelga intentando construir la tabla, lo que el usuario percibe como "no carga".
- **Resolucion**: agregado `AND (@idEmpresa IS NULL OR c.idEmpresa = @idEmpresa)` al `WHERE` de `#AllCortes` (mismo patron NULL-safe que ya usa el filtro de `#Sucursales` en el mismo SP), via `ALTER PROCEDURE`. **No se toco la RLS ni la funcion `fn_rls_empresa_o_global_v2`** — siguen dejando pasar el catalogo global para otros usos legitimos (ej. adoptar productos del catalogo). El fix es un filtro de negocio adicional, propio de esta consulta puntual, igual que el patron ya documentado para `dbo.buscarEmbutido` (2026-07-31, arriba). **Aplicado solo en la base local (`.\sqlexpress`) de esta PC** — falta aplicar el mismo `ALTER PROCEDURE` en el/los servidores reales (VM `carnisys.com` y/o SM) cuando el usuario lo confirme, ya que los SPs no estan versionados en este repo. Backup de la definicion original en el scratchpad de la sesion (`a_ExistenciaStockPorSucursales_backup_20260801.sql`, no versionado).
- **Resultado verificado**: SP a mano, tras el fix: **1.1 segundos**, ~112-172 filas (segun filtros). En Chrome real (CDP), clic en "Buscar" y la tabla queda poblada con datos reales en ~260ms.
- **Leccion**: cuando una tabla tiene RLS con un predicado que deliberadamente deja ver mas de lo que una consulta puntual necesita (ej. "empresa o global"), cada SP que la usa **todavia necesita su propio filtro de negocio** ademas de lo que la RLS permite ver — la RLS es el techo de seguridad, no el filtro funcional de cada pantalla. Ante una pantalla lenta que junta datos de una tabla con RLS conocida, medir cuantas filas devuelve el SP en crudo (`SET STATISTICS TIME ON` + contar filas) antes de asumir que es un problema de infraestructura (RAM, IIS, etc.).

## REGLA - Stored procedures sobre `dbo.Corte` necesitan su propio filtro de empresa, la RLS no alcanza (3 veces, 2026-08-01)

- **Ocurrencias**: `dbo.a_ExistenciaStockPorSucursales` (arriba), `dbo.a_CierreStock` (Stock Actual/Cierre Stock/Stock Retroactivo en `/Reportes`) y `dbo.Acum_Ventas` (Proyeccion Ventas vs Stock en `/Reportes`) — las 3 arman "todos los productos" (`AllCortes` o equivalente) sobre `dbo.Corte` sin filtrar por `idEmpresa`, confiando en que la RLS (`fn_rls_empresa_o_global_v2`, que a proposito deja ver empresa + catalogo global) ya alcanza. `Acum_Ventas` es el caso mas sutil: **si tenia** `@idEmpresa`, pero lo aplicaba con el mismo patron "empresa o global" (`ISNULL(idEmpresa,0) IN (0, @idEmpresaFiltro)`) que usa la RLS — replicando el problema en vez de evitarlo.
- **Causa raiz**: alguien parece haber tomado el patron "empresa o catalogo global" (correcto y deliberado para la RLS, y para el flujo real de "agregar producto desde catalogo global" en Productos) y lo replico en SPs de reportes/stock que **no** deberian ver el catalogo global — ahi el patron correcto es simplemente `idEmpresa = @idEmpresa`, sin el `OR ... = 0`.
- **Verificacion rapida**: `SET STATISTICS TIME ON` + contar filas del SP ejecutado a mano. Un salto de docenas/cientos de filas esperadas a ~100K+ filas devueltas es la señal inequivoca.
- **REGLA**: antes de dar por buena una consulta que junta datos de `dbo.Corte` (o cualquier tabla con RLS "empresa o global" conocida), preguntarse explicitamente: *¿esta pantalla necesita ver el catalogo global, o solo los productos propios de la empresa?* Si es lo segundo (la gran mayoria de los casos — stock, reportes, movimientos, ventas), el filtro tiene que ser `idEmpresa = @idEmpresa` a secas, nunca `IN (0, @idEmpresa)` ni delegarlo a la RLS sola. El unico lugar confirmado que necesita ver el catalogo global es el flujo de "agregar producto" (nuevo producto / importar desde catalogo global) en `Productos`.
- **Efecto secundario encontrado en `a_CierreStock`**: ademas de la falta de filtro, varios bloques del SP hacen self-join de `dbo.Corte` contra si mismo por `idCorteMaestro` (para sumar sub-cortes a su corte maestro) — sin indice en esa columna, sobre ~102K filas eso es carisimo aparte del volumen. Se agrego `IX_Corte_idCorteMaestro` (indice cubriente, aditivo, sin riesgo). Si una consulta hace self-join de `Corte` por `idCorteMaestro`, revisar si existe ese indice antes de asumir que el filtro de empresa solo ya alcanza.

## LECCION (no bug de codigo) - Plan de ejecucion cacheado con parametros de prueba puede simular un bug que no existe

- **Sintoma**: despues de corregir `a_CierreStock` y `Acum_Ventas` (arriba) y verificar cada uno por separado con `@idEmpresa=1` (rapido), la pantalla `/Reportes` con "Proyeccion Ventas vs Stock" seguia dando timeout SQL en Chrome real.
- **Causa**: durante el diagnostico se habian ejecutado ambos SPs a mano varias veces con parametros distintos, incluyendo `@idEmpresa = 0` (a proposito, para confirmar la hipotesis del bug) y sin pasar `@idEmpresa` en absoluto. SQL Server cachea **un** plan de ejecucion por stored procedure (no por combinacion de valores de parametros) — el plan quedo optimizado para la selectividad "trae casi todo" de esas pruebas, y las llamadas reales posteriores con `@idEmpresa=1` (selectivo, pocas filas) seguian reusando ese plan lento (parameter sniffing clasico).
- **Verificacion**: `EXEC sp_recompile 'dbo.a_CierreStock'; EXEC sp_recompile 'dbo.Acum_Ventas';` y reintentar — la pantalla paso de timeout a ~1 segundo sin ningun otro cambio.
- **Leccion**: al diagnosticar o corregir un SP, si se lo ejecuta a mano repetidas veces con parametros de prueba muy distintos entre si (sobre todo alguno deliberadamente "ancho", como `idEmpresa=0` para reproducir un bug), el plan cacheado puede quedar sesgado para esas pruebas. Antes de concluir "el fix no alcanzo" por un timeout que reaparece **despues** de verificar el fix aislado, probar `sp_recompile` sobre el/los SPs tocados — mas barato que seguir buscando un bug de codigo que no esta ahi. No hace falta esta precaucion al aplicar el mismo fix en un servidor real: ahi el primer llamador siempre es una request real con un `idEmpresa` valido, nunca los valores extremos usados solo para probar.

## REGLA - `width: 100%`/`min-width: 100%` en un input que despues entra a un `.input-group` rompe el layout (2da vez, 2026-08-01)

- **Sintoma** (2da ocurrencia; la 1ra fue el filtro de "Mis actividades" del 2026-07-31, arriba): al agregar el boton de escanear codigo de barra al lado de `#txtCodigoProducto` en `Movimientos/Editar.cshtml`, el input se iba a su propia fila en vez de quedar pegado al boton.
- **Causa**: `.movimiento-input-codigo` (pensada para un input suelto, sin boton al lado) tenia `width:100%; min-width:100%`. Al envolver el input en un `.input-group` (flexbox con `flex-wrap:wrap`), el motor de flexbox decide en que fila entra cada item usando su **ancho preferido** (`flex-basis`, que con `auto` cae en la propiedad `width`) — un input con `width:100%`/`min-width:100%` "pide" casi todo el ancho del contenedor antes de que el shrink pueda actuar, asi que el boton y el input no entran juntos en la misma linea.
- **Intento fallido**: pisar con `width:auto` en vez de `width:100%` **no alcanza** — `auto` cae al ancho nativo del `<input>` (~190px en Chrome), que sigue siendo mas ancho que el hueco libre junto al boton.
- **Resolucion**: `width: 1%` (no `auto`), igual que hace Bootstrap en su propio `.input-group > .form-control { flex: 1 1 auto; width: 1%; }`. Un ancho preferido chico saca al input de la decision de wrap; el `flex-grow:1` despues lo estira para ocupar el resto de la fila.
- **REGLA**: cualquier input con `width:100%`/`min-width:100%` (o `width:auto`) fijado por su propia clase, si en algun momento pasa a vivir dentro de un `.input-group` (le agregan un boton/icono al lado), hay que pisarle `width: 1%` scopeado a ese contexto (`.input-group .mi-clase { width: 1%; min-width: 0; flex: 1 1 auto; }`), no `auto`. Antes de asumir que el problema es "el boton no entra", medir el `flex-basis` resuelto del input, no solo su `width` nominal.

## REGLA - Color claro hardcodeado sin variante oscura, sobre el sistema de temas real de `_LayoutBase.cshtml` (2 veces, 2026-08-01)

- **Sintoma** (1ra vez: `.app-product-highlight`, el input "Producto" resaltado en 6 vistas — Movimientos, Stock, Elaborados/Carga, PuntosExpendio/Abrir, Elaborados/EditarIngresoRapido, Compras/Editar; 2da vez: `.fecha-mobile-picker`, el selector de fecha+hora mobile de `/Ventas`): con modo oscuro activo, un elemento puntual queda con fondo claro mientras el resto de la pagina esta correctamente oscura.
- **Causa**: en paginas con `_LayoutBase.cshtml` (la gran mayoria del sistema — **no** `_LayoutPOS.cshtml`, que es el unico que carga `dark-mode.css`), el modo oscuro real lo da `Content/css/ui-refresh.css` via variables CSS (`--ui-input-bg`, `--ui-surface-alt`, `--ui-border`, etc.) redefinidas bajo `html.dark-mode body.app-shell` / `body.app-shell.dark-mode`. Una clase puntual con un color fijo (`background:#f8fbff`, `background:#f8fafc`, etc.) escrita para el caso general en modo claro, sin variante oscura, no queda cubierta por esas reglas — y si ademas usa `!important` (caso 1), directamente le gana al sistema de temas real aunque este si tenga la regla correcta.
- **Verificacion**: medido con Chrome real el `background-color` computado del elemento en cuestion con `html.dark-mode`/`body.dark-mode` activos — sigue devolviendo el color claro hardcodeado en vez de la variable `--ui-*` esperada.
- **Resolucion**: override puntual `html.dark-mode body.app-shell .mi-clase, body.app-shell.dark-mode .mi-clase { background: var(--ui-input-bg | --ui-surface-alt | lo que corresponda); border-color: var(--ui-border); }`, reusando las mismas variables que ya usa el resto de la app (nunca un color fijo nuevo).
- **REGLA**: cualquier clase nueva (o existente) con un color de fondo/borde/texto fijo en hex, sobre todo si ademas usa `!important`, hay que revisar si el elemento vive bajo `_LayoutBase.cshtml` y si el color tiene cubierta su variante `html.dark-mode`/`body.app-shell.dark-mode`. Antes de dar por resuelto un fix de modo oscuro en una vista, probar esa vista puntual con Chrome real y modo oscuro activo — no alcanza con que el contenedor general se vea bien.
