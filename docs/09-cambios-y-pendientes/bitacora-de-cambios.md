## 2026-08-04 (continuacion, mas reciente) - Script de backfill: sembrar dbo.CortePuntoStockSucursal para productos con enCierreStock activado

- Cambio: script nuevo `Datos/DB-Procedures/20260804-Backfill_CortePuntoStockSucursal_EnCierreStock.sql` para el caso puntual pedido por el usuario: crear la fila Producto x Sucursal (`dbo.CortePuntoStockSucursal`) para todo producto de empresa (`idEmpresa > 0`, nunca catalogo global) con `enCierreStock = 1`, en cada sucursal de esa misma empresa, tomando `dbo.Corte.puntoStock` como valor de referencia (0 si es NULL). Es un script manual, separado del backfill generico de `20260803-Create_CortePuntoStockSucursal.sql` (ese sembro TODOS los productos sin filtrar por `enCierreStock` y queda inerte para siempre una vez que la tabla existe — no cubre productos que activen `enCierreStock` mas adelante, ni sirve para reintentar si en algun servidor no llego a insertar nada). El nuevo script es idempotente (`NOT EXISTS` fila por fila, se puede correr las veces que haga falta) y setea `SESSION_CONTEXT('EsAdminCarniSys')=1` (guardado detras de `IF OBJECT_ID('sys.sp_set_session_context')...` para no romper en SQL Server 2008) para poder leer todas las empresas pese a la RLS de `dbo.Corte`.
- **Hallazgo aparte, no corregido (fuera de lo pedido)**: al leer la definicion real de la RLS de `dbo.Corte` (`fn_rls_empresa_o_global_v2`, via `OBJECT_DEFINITION`) se confirmo que bloquea TODAS las filas salvo que la sesion sea el login `cs_admin`, tenga `SESSION_CONTEXT('EsAdminCarniSys')=1`, o `SESSION_CONTEXT('IdEmpresa')` coincida — no hay excepcion implicita para `sa`/sysadmin en RLS de SQL Server. El script hermano `20260803-Create_CortePuntoStockSucursal.sql` (todavia no corrido en un servidor con datos reales) **no setea ese session context**: si se corre tal cual via `sqlcmd`/SSMS sin session context propio, el `CREATE TABLE` va a andar pero el `INSERT...SELECT` va a ver cero filas de `dbo.Corte` por la RLS, y el script va a imprimir "creada e inicializada correctamente" de forma enganosa habiendo insertado 0 filas. No lo toque porque no era parte de este pedido (§5, scope acotado) — si ese script todavia esta pendiente de correr en algun servidor, agregarle el mismo `EXEC sys.sp_set_session_context @key=N'EsAdminCarniSys', @value=1` (guardado igual que en el script nuevo) antes de usarlo.
- Archivos o modulos afectados: `Datos/DB-Procedures/20260804-Backfill_CortePuntoStockSucursal_EnCierreStock.sql` (nuevo). No se modifico ningun archivo existente.
- Motivo: pedido explicito del usuario. Se le pregunto si sumar tambien el filtro `independiente = 1` (patron usado en otras queries del repo para "productos vendibles") y eligio dejarlo solo con `enCierreStock`, tal cual lo pidio originalmente.
- Resultado: **verificado con datos reales** contra la base local (`.\sqlexpress`/`carnisys`), dentro de una transaccion con `ROLLBACK` (sin dejar cambios persistentes): se tomo un producto real (`idCorte=1`, `idEmpresa=2`, `enCierreStock=1`), se borraron sus 2 filas existentes en `CortePuntoStockSucursal` para simular un gap, se corrio la logica del backfill y reinsertó exactamente esas 2 filas con el `puntoStock` correcto; una segunda corrida inmediata inserto 0 filas (idempotencia confirmada); se confirmo que ningun producto de `idEmpresa=0` tiene fila propia en la tabla.
- **Ejecutado de verdad (mismo dia, a pedido explicito del usuario)** contra la base local `.\sqlexpress`/`carnisys`: `0 fila(s) insertadas` — esperado, ya que el backfill generico del 2026-08-03 (sin filtro `enCierreStock`) ya habia sembrado ese mismo set de 100 filas antes. Verificado post-ejecucion: `128` filas totales en la tabla (sin cambios, coherente con 0 inserciones) y `0` grupos duplicados por `(idEmpresa, idCorte, idSucursal)` (`GROUP BY ... HAVING COUNT(*) > 1` vacio) — confirma que la clausula `NOT EXISTS` no duplico nada. Durante la verificacion post-ejecucion `sqlcmd` tiro dos timeouts de login transitorios (`Shared Memory Provider: Timeout error [258]`); la maquina tenia ~325MB de RAM libre de ~7GB en ese momento — mismo patron ya documentado en `docs/07-operacion-y-soporte/incidencias-frecuentes.md` (incidente 2026-07-31), no relacionado al script. Se resolvio reintentando con `-l 30` (timeout de login mas largo), sin necesidad de liberar memoria esta vez. **No se corrio en ningun otro servidor** (San Martin, San Lorenzo, produccion) — si se necesita ahi, correrlo a mano con backup previo si hay datos reales.
